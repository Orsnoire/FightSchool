## Implementation

- `quests.ts` selects the affected quest audience/objective in SQL. Evidence events
  use their hosting guild, students and fight; results evaluate totals/evidence;
  character-level events reach all current memberships. Membership changes,
  teacher progression/quest edits and question-bank edits have explicit hooks.
  Completed objectives with all relevant receipts are skipped on normal events.
- `quest-data.ts` computes scalar evidence aggregates in SQL, cached by equivalent
  criteria within an evaluation. It uses durable evidence before legacy result
  fallback, and never invents question mastery from aggregate results. Weekly
  windows retain the existing UTC epoch-week rule, weighted class accuracy excludes
  non-victorious/departed participants, and mastery retains their correct keys.
- Level/grant lookup maps and member contexts are built once. Historical totals
  return at most two aggregate rows per student instead of full result documents.
  Only referenced mastery question banks are read; generic seeded milestones do
  not load teacher fight definitions. Unprefixed persisted question keys are
  explicitly version 1 and remain byte-compatible with existing rooms/evidence.
- Quest/shop GET requests perform no seeding or reward writes. Teachers have an
  explicit **Refresh quest progress** action (`POST /api/guilds/:id/quests/reconcile`)
  for missing legacy seeds, imported history or an interrupted authoring operation.
  It is owner-only, idempotent and unavailable for archived guilds. New guilds and
  member joins retain their seed hooks. Ordinary reads need no initialization writes.
- Awards still pass through `award_quest_batch` and
  `award_combat_results_with_stamina`. Global personal receipts prevent duplicate
  milestone gold across guilds; per-quest and combat receipts remain untouched.
  Newly awarded grants/XP/tier changes revisit only their progression dependencies.
  Existing completed rewards also supply durable dependency receipts: if an award
  commits and its acknowledgement or a downstream evaluation fails, retry traverses
  those dependencies without repaying the source quest. Each dependency set is
  replayed once per traversal; fresh grants can continue a finite cascade. Permanent
  grants/XP remain recoverable even if a weekly boundary passes during the outage.
  Derived guild level updates use an experience guard against a slower room
  overwriting a newer level.
- Room snapshots remain the durable evidence outbox. A failed projection/evaluation
  keeps the pending marker until the entire operation succeeds; replay runs even
  if the evidence UPSERT already committed. Outstanding evidence retries are
  coalesced across the next answer burst and retried by a restored room alarm.
  Normal evidence is produced at **combat resolution**, not for each raw answer;
  this change does not claim a new normal-path 30-to-1 evidence reduction.
- Student/fight/class combat history uses a stable descending `(completed_at,id)`
  keyset, default 50 rows, maximum 100, and an `X-Next-Cursor` header. Student UI
  loads 10 fights per page and fetches separate all-time SQL aggregates, so its
  headline statistics are not truncated to the displayed page. Names join in SQL.
  Leaderboards aggregate in SQL and preserve weighted accuracy/hidden metrics;
  historical loot authorization returns distinct item IDs instead of all loot rows.

## Reproducible measurements

Local Node **24.19.0**, locked dependencies, PGlite PostgreSQL, no network database.
Each guild fixture has 30 or 60 members, **2,051 or 4,091 seeded quests**, 100 historical
results per member, a 20-question bank, and an equally populated second guild.
Half of results have durable per-question evidence; the other half exercise legacy
fallback. Each full evaluation is rolled back to the same unawarded fixture.
Three full-evaluation runs are recorded; times below are medians, not live SLOs.
Rows/bytes count SQL responses at the PGlite query boundary, not browser payloads
or Neon billing. Fixture setup and transaction controls are excluded.

| Equivalent full reconciliation | 30 members before → after | 60 members before → after |
| --- | --- | --- |
| SQL calls | 11 → 13 | 11 → 13 |
| Returned rows | 6,645 → 2,155 | 13,275 → 4,285 |
| Returned JSON bytes | 3,504,115 → 629,883 (**82.0% less**) | 7,002,985 → 1,255,953 (**82.1% less**) |
| Local elapsed time, median | 504.92 → 126.32 ms | 1,501.33 → 210.46 ms |

The two additional full-evaluation queries reconstruct reward dependencies from durable
completions, preserving recovery when a quest SQL acknowledgement is lost. They do
not load historical evidence payloads. The intentionally full teacher reconciliation
still returns all quest views. Normal
requests/events now do less work:

| New workload | Quests (30 / 60 members) | SQL calls | Returned bytes (30 / 60 members) |
| --- | --- | --- | --- |
| Student quest read | 79 / 79 | 6 | 30,363 / 36,783 |
| One student's result event (totals/evidence) | 11 / 11 | 13 on first award | 10,233 / 16,653 |
| Resolved-question evidence event | 2 / 2 | 6 | 3,734 / 6,644 |

The separate character-level event checks that student's 68 seeded milestones in
each membership; it does not load peers' personal milestones. Result-event numbers
above exclude that separate stage and are not whole-room completion timings.
Student view SQL response bytes are **99.1% / 99.5% below** the old full-guild
GET evaluator. Reads no longer invoke atomic awards at all.

The outage/retry fixture starts with a previous resolved question awaiting evidence
projection, then submits 30/60 new answers while SQL is unavailable:

| Metric | 30 players before → after | 60 players before → after |
| --- | --- | --- |
| Evidence projection attempts during burst | 31 → 1 | 61 → 1 |
| Recovery alarm attempts after restore | 1 → 1 | 1 → 1 |
| Durable command receipts retained | 30 → 30 | 60 → 60 |
| Checkpoints including recovery | 64 → 64 | 124 → 124 |
| Checkpoint bytes | 3,334,070 → 3,334,070 | 12,573,568 → 12,573,568 |

There is no claimed reduction in durable checkpoint work or a new network latency

## Index decisions and migration

Candidate `EXPLAIN (ANALYZE,BUFFERS,FORMAT JSON)` plans were captured on the old
schema **before adding production indexes**. The selectivity fixture contains
102 guilds, 3,030 students, 36,000 results and 2,051 quests. No planner switches
force index usage.

| Added index | Observed query change | Sample execution, before → after |
| --- | --- | --- |
| `guild_memberships_student_idx` | Selective student membership lookup stops scanning all memberships | 0.503 → 0.044 ms |
| `combat_results_student_history_idx` | Ordered student page uses index and limit instead of scan/sort | 6.082 → 0.136 ms |
| `combat_results_guild_history_idx` | Ordered guild page uses index and limit | 11.731 → 0.156 ms |
| `combat_results_fight_history_idx` | Ordered fight page uses index and limit | 34.739 → 0.148 ms |
| `quests_guild_student_idx` | Shared + one-student quest selection accesses the matching audience | 0.352 → 0.194 ms |

These single candidate timings support the structural plans, not a repeatable
latency threshold. Existing `quest_evidence_guild_student` and
`studentJobLevels_pair_unique` already serve their relevant lookups; no redundant
replacement was added. Full-guild totals still necessarily inspect relevant
history in PostgreSQL; this is not a maintained cumulative-total table.

Migration **0017 is index-only**, with matching schema/snapshot/journal. It does
not rewrite prior SQL, delete data, reset progression, alter reward procedures,
or change the durable room format. Its descending indexes explicitly use
`NULLS FIRST` to match the queries: final plans and a regression test verify the
student history page has no extra sort. A normal index build acquires database
locks; the authorized release migration gate passed at 22:30:55 UTC. No separate
per-index build timing or live EXPLAIN was captured; production sizing/load work remains C12.
No production migration ran during the initial implementation-only phase.

A code rollback can leave these additive indexes in place. Existing evidence,
receipts, students, inventory, job levels, guilds, results and permissions remain
compatible with the prior runtime; no reverse data migration is needed.

## Verification and limits

Local gates: TypeScript; the complete automated suite (275 tests); production
client/Worker builds; whitespace check. Focused checks additionally cover:

- Exact progress/completion parity against the pinned baseline in a 30-member guild.
- Read-only HTTP quest/shop endpoints and scoped student SQL/permissions.
- SQL/legacy evidence precedence, weekly edges, weighted class accuracy, question
  edits, solo/mode constraints, departed-player mastery and stale revision rejection.
- Failure after committed evidence, lost acknowledgement after committed combat
  awards, replay, two interleaved room completions, global milestone receipts and
  statement-level reward rollback with no partial guild XP or completion receipt.
  A separate regression loses acknowledgements after each of three committed quest
  award stages and verifies recovery through shared grants to another student and
  a guild-level milestone, with no repeated payment.
- 30/60-player pending evidence coalescing, retained receipts and restored-object alarm.
- Equal-timestamp keyset pagination, limits/cursor validation, all-time summaries,
  ownership, UI load-more/retry, and explicit teacher reconciliation.
- Populated-data preservation through 0017, no-op schema generation, migrated
  catalog consistency and immutable shipped migration history.
